# =============================================================================
# Backend Python dependency manifest - Used Car Marketplace API
# =============================================================================
#
# This manifest repairs an already-referenced-but-missing file. Two committed
# tool invocations read it, and neither can work without it:
#
#   .github/workflows/backend_ci.yml:L24  ->  pip install -r requirements.txt
#   scripts/setup_environment.sh:L28      ->  pip install -r requirements.txt
#
# Every requirement below is an exact `==` pin. There are deliberately no
# ranges, no `latest`, and no unpinned names: the whole set is resolved and
# installed together on CPython 3.9.25, so these versions are known to be
# mutually consistent rather than merely plausible. Each pin is annotated with
# the module that imports it, so the manifest documents its own justification.
#
# -----------------------------------------------------------------------------
# FIXED INVENTORY: THE SEVENTEEN PLANNED LINES, PLUS TWO AUTHORISED ADDITIONS
# -----------------------------------------------------------------------------
# The package set is not a matter of local judgement. Adding a line - even a
# well-intentioned compatibility pin, and even for a package already present in
# the resolved closure as a transitive dependency - is a deviation, and needs
# authorising as its own reviewed change rather than being smuggled in
# alongside a feature.
#
# There are exactly TWO additions to the seventeen planned lines, and each
# carries that authorisation:
#
#   * `google-api-core==2.30.3` - not a compatibility pin. The rule above
#     governs packages this codebase does not import; google-api-core IS
#     imported directly, by name, at app/services/rating.py, where
#     `google.api_core.exceptions` is what tells a duplicate vote apart from a
#     retryable fault. A distribution whose EXCEPTION IDENTITY the feature's
#     correctness depends on must not float with a transitive resolution.
#     Declaring it is the same discipline that fixes the other seventeen, not
#     an exception to it. See the Google Cloud section for its compatibility
#     statement.
#   * `bcrypt==4.0.1` - a compatibility pin, and exactly the kind this header
#     says must be authorised separately rather than assumed. Code review
#     finding M5 is that authorisation. See RESOLVED FINDING 3 below for the
#     measurements, and the Authentication section for the pin itself.
#
# Two further consequences are worth naming, because both were previously
# mistaken for missing requirements:
#
#   * python-dotenv is ALREADY in the closure. `uvicorn[standard]==0.23.2`
#     declares `python-dotenv>=0.13` in its `standard` extra, which is what
#     makes the `env_file = ".env"` declaration at app/core/config.py:L21-L23
#     work. It needs no line of its own.
#   * redis is NOT needed. See the background-tasks section below.
#
# -----------------------------------------------------------------------------
# LOAD-BEARING CONSTRAINT: pydantic MUST stay on the 1.x line
# -----------------------------------------------------------------------------
# backend/app/core/config.py:L1 is `from pydantic import BaseSettings`, and
# Pydantic v2 removed `BaseSettings` from the top-level package (it moved to
# the separate pydantic-settings distribution). Every Pydantic model in this
# codebase is written to v1 semantics as a result. Weakening this pin makes
# app/core/config.py fail to import, and with it every module that imports
# `settings` - which is to say all of them.
#
# -----------------------------------------------------------------------------
# RECORDED FINDING 1: Python 3.9 is past end of life
# -----------------------------------------------------------------------------
# `google-api-core` and `google-auth` emit unsupported-runtime warnings when
# imported on Python 3.9. That warning is a genuine forward-compatibility
# signal, so it is recorded here rather than suppressed. The runtime target is
# NOT raised unilaterally: .github/workflows/backend_ci.yml:L16-L19 pins
# `python-version: '3.9'` and is the only version source in the repository -
# there is no setup.py, pyproject.toml, tox.ini, setup.cfg or .python-version
# anywhere to widen it - so this manifest honours the documented runtime.
#
# -----------------------------------------------------------------------------
# RECORDED FINDING 2: CI resolves this path from the repository root
# -----------------------------------------------------------------------------
# .github/workflows/backend_ci.yml declares no `working-directory:` key, so its
# L24 `pip install -r requirements.txt` resolves to ./requirements.txt at the
# repository root rather than to backend/requirements.txt. scripts/
# setup_environment.sh:L28 has the same problem. This is a PRE-EXISTING
# workflow defect and it is recorded, not fixed: the workflow files are
# explicitly no-change, and this manifest's path is fixed at
# backend/requirements.txt. No duplicate copy is placed at the repository root.
#
# -----------------------------------------------------------------------------
# RESOLVED FINDING 3: passlib 1.7.4 drives only bcrypt < 4.1 cleanly
# -----------------------------------------------------------------------------
# `passlib[bcrypt]==1.7.4` below resolves bcrypt through passlib's own extra,
# which declares `bcrypt>=3.1.0` with NO upper bound. A clean resolution on
# CPython 3.9.25 therefore installs bcrypt 5.0.0 today, and that combination
# does not work. Measured against the CryptContext at app/api/auth.py:L13:
#
#   bcrypt 4.0.1          -> hash()/verify() correct and silent
#   bcrypt 4.1.1 - 4.3.0  -> correct, but each call logs a "(trapped) error
#                            reading bcrypt version" traceback, because
#                            bcrypt >= 4.1 removed the `bcrypt.__about__`
#                            attribute passlib's version probe reads
#   bcrypt 5.0.0          -> BROKEN: passlib's backend probe hashes a >72-byte
#                            secret to detect an old wrap bug, and bcrypt 5.x
#                            raises `ValueError: password cannot be longer
#                            than 72 bytes` instead of truncating, so
#                            hash()/verify() raise instead of working
#
# The blast radius today is zero: app/api/auth.py:L21 mounts a router with NO
# routes, so verify_password(), get_password_hash() and authenticate_user() are
# not reachable from any endpoint - registration and login are F-001 work and
# are out of scope. It becomes load-bearing the moment a login handler lands.
#
# RESOLUTION: the `bcrypt==4.0.1` constraint IS now taken, below. This note
# said the deviation had to be authorised as its own reviewed change rather
# than smuggled in with a feature; code review finding M5 is that
# authorisation. 4.0.1 is the only pairing measured both correct and silent
# above, and holding there trades away no security to buy that compatibility:
# bcrypt has zero published advisories at any version (checked against
# OSV.dev), so there is no fix being declined by not moving to 5.x.
# Re-verified after pinning: CryptContext(schemes=['bcrypt']) hashes and
# verifies correctly and emits no "(trapped)" traceback.
#
# -----------------------------------------------------------------------------
# RESOLVED FINDING 4: the TRANSITIVE graph beneath these pins is now locked
# -----------------------------------------------------------------------------
# Every line in this file is an exact pin, but the nineteen packages below pull
# in roughly fifty more, and until this finding was resolved those fifty were
# free to float: two installs a week apart could resolve different versions of
# grpcio, protobuf, cryptography or starlette from an identical manifest, so
# "resolved and installed together" held for the direct pins but not for the
# graph beneath them.
#
# A committed lock artifact (`pip install -c constraints.txt`) is the standard
# closure of that gap and needs no workflow change.
#
# RESOLUTION: that lock IS now committed, as backend/constraints.txt, under
# code review finding M5. This note correctly identified that the two
# decisions are coupled - a lock of the full closure necessarily pins bcrypt -
# so both are taken together in this single reviewed change: bcrypt is pinned
# to the measured-clean 4.0.1 below, and constraints.txt was generated from
# the environment that pin produces. The lock therefore records 4.0.1 rather
# than the broken 5.0.0 a clean unconstrained resolve would have chosen.
#
# To install the exact verified closure:
#     pip install -r requirements.txt -c constraints.txt
#
# requirements.txt alone remains installable, and that is what CI runs today -
# the constraints file is additive and pins only the transitive graph, so it
# changes no direct pin and needs no workflow edit.
# =============================================================================


# --- Web framework and ASGI server -------------------------------------------

# ASGI framework and the Depends() dependency-injection primitive that every
# route guard is built on - app/main.py:L1 and all four routers. The 0.103.x
# line is the FastAPI series that is compatible with Pydantic v1.
fastapi==0.103.2

# ASGI server. Nothing else in the repository declared one, so `uvicorn
# app.main:app` was previously unrunnable from a clean checkout.
uvicorn[standard]==0.23.2

# Multipart/form-data parsing. FastAPI requires it for the
# OAuth2PasswordRequestForm imported at app/api/auth.py:L2.
#
# Raised 0.0.6 -> 0.0.20 for code review finding M8. 0.0.6 is affected by
# CVE-2024-24762 (ReDoS in Content-Type option parsing, fixed in 0.0.7) and
# CVE-2024-53981 (excessive-logging denial of service on malformed multipart
# boundaries, fixed in 0.0.18). 0.0.20 clears both.
#
# 0.0.20 is the CEILING on this runtime, not a preference: every release from
# 0.0.21 onward declares `requires-python >= 3.10`, while backend_ci.yml pins
# 3.9 and that runtime is fixed as no-change. Advisories fixed only in 0.0.22
# and later are therefore unreachable here without first raising the Python
# target, which is a platform decision outside this change. That residual is
# recorded rather than silently absorbed.
#
# Compatibility verified rather than assumed: starlette 0.27.0 - the release
# fastapi 0.103.2 resolves - imports the LEGACY module name, at
# formparsers.py:L10 `import multipart` and requests.py:L14
# `from multipart.multipart import parse_options_header`. 0.0.20 still ships
# that module alongside the renamed `python_multipart` package, so both import
# paths resolve, and a form-encoded POST through OAuth2PasswordRequestForm
# returns 200.
python-multipart==0.0.20


# --- Validation and settings -------------------------------------------------

# Request/response models and BaseSettings configuration. v1 is MANDATORY, not
# preferential - see the LOAD-BEARING CONSTRAINT note above.
#
# Note on `.env` support, which pydantic v1 delegates to python-dotenv: reading
# an `env_file` without python-dotenv installed raises `ImportError:
# python-dotenv is not installed, run pip install pydantic[dotenv]` from
# pydantic/env_settings.py, and app/core/config.py:L21-L23 declares
# `env_file = ".env"` while the repository's own instructions produce that file
# (scripts/setup_environment.sh:L40 runs `cp .env.example .env`; README.md:
# L48-L49 says the same). No separate requirement is needed for it: python-
# dotenv arrives in the closure through the `uvicorn[standard]` extra above,
# which declares `python-dotenv>=0.13`. Verified on CPython 3.9.25 - installing
# this manifest yields a working python-dotenv, so the documented
# `cp .env.example .env` path configures the application rather than breaking
# it. Do not add a python-dotenv line to "make sure": it is already there.
pydantic==1.10.13


# --- Authentication ----------------------------------------------------------

# JWT encode/decode - app/api/auth.py:L3 and app/core/security.py:L2. The
# [cryptography] extra supplies the signing backend the HS256 algorithm needs.
#
# Raised 3.3.0 -> 3.5.0 for code review finding m8. 3.3.0 is affected by
# CVE-2024-33663 (algorithm confusion when an OpenSSH ECDSA public key is
# supplied, rated CRITICAL) and CVE-2024-33664 (JWE decompression bomb causing
# denial of service). Both are fixed in 3.4.0; 3.5.0 is the current release of
# that line and carries no known advisory. It still declares
# `requires-python >= 3.9`, so it fits the pinned runtime with no runtime
# change. Re-verified after upgrading against the exact code path in
# app/api/auth.py: an HS256 encode/decode round trip returns the original
# claims, and a tampered signature raises JWTError instead of validating.
python-jose[cryptography]==3.5.0

# Password hashing - app/api/auth.py:L4,L13 and app/core/security.py:L3,L9
# build a CryptContext(schemes=['bcrypt']). The `[bcrypt]` extra brings the
# bcrypt backend into the closure, but declares only `bcrypt>=3.1.0` with no
# upper bound - so the backend has to be pinned explicitly on its own line
# below. See RESOLVED FINDING 3 in the header for the measurements.
passlib[bcrypt]==1.7.4

# The bcrypt backend passlib drives, pinned for code review finding M5.
# Without this line a clean resolve installs bcrypt 5.0.0, which BREAKS passlib
# 1.7.4: passlib's backend probe hashes a >72-byte secret to detect an old wrap
# bug, and bcrypt 5.x raises `ValueError: password cannot be longer than 72
# bytes` instead of truncating, so hash() and verify() raise instead of
# working. 4.0.1 is the only version measured both correct AND silent;
# 4.1.1-4.3.0 hash correctly but log a "(trapped) error reading bcrypt
# version" traceback on every call, because bcrypt >= 4.1 removed the
# `bcrypt.__about__` attribute that passlib's version probe reads.
bcrypt==4.0.1

# --- Background tasks --------------------------------------------------------

# Task queue - app/tasks/background_jobs.py:L1-L2 (`from celery import Celery`
# and `from celery.schedules import crontab`).
#
# Declared BARE, with no broker extra. The worker tier is aspirational in this
# build and nothing may depend on it: no task is ever dispatched, no
# .delay()/apply_async() call exists anywhere, and the module cannot even be
# imported. app/tasks/background_jobs.py:L9 constructs
# `Celery(..., broker=settings.CELERY_BROKER_URL)` at import time against a
# field app/core/config.py never declares, so the import raises AttributeError
# long before any transport is selected - which is also why no `redis://` URL
# is ever handed to kombu and no redis client is ever loaded. Adding a broker
# extra here would install a client for a broker that is neither configured
# (CELERY_BROKER_URL is a commented recorded finding in backend/.env.example,
# not a Settings field) nor provisioned. The rating feature is correct without
# it: the read paths publish an expired rating opportunistically on encounter.
celery==5.3.6
