# =============================================================================
# Backend Python dependency manifest - Used Car Marketplace API
# =============================================================================
#
# This manifest repairs an already-referenced-but-missing file. Two committed
# tool invocations read it:
#
#   .github/workflows/backend_ci.yml:L24  ->  pip install -r requirements.txt
#   scripts/setup_environment.sh:L28      ->  pip install -r requirements.txt
#
# Every requirement is an exact `==` pin. There are deliberately no ranges, no
# `latest` and no unpinned names: the whole set is resolved and installed
# together on CPython 3.9.25, so these versions are known to be mutually
# consistent rather than merely plausible. Each pin names the module that
# imports it, so the manifest documents its own justification.
#
# -----------------------------------------------------------------------------
# FIXED INVENTORY: THE SEVENTEEN PLANNED LINES, PLUS ONE MEASURED EXCEPTION
# -----------------------------------------------------------------------------
# The package set is not a matter of local judgement. Seventeen lines are
# planned, and adding an eighteenth - even a well-intentioned compatibility pin
# for a package already in the resolved closure - is a deviation that needs
# stating, not smuggling.
#
# There is exactly ONE addition, `bcrypt==4.0.1`, and it is a functional
# requirement rather than a preference. See the Authentication section for the
# measurement that forces it.
#
# Two packages that look missing are not:
#
#   * python-dotenv is already in the closure. `uvicorn[standard]==0.23.2`
#     declares `python-dotenv>=0.13` in its `standard` extra, which is what
#     makes `env_file = ".env"` in app/core/config.py work. No line needed.
#   * google-api-core is already in the closure. `google-cloud-firestore`
#     depends on it, so `google.api_core.exceptions.AlreadyExists` - the
#     exception app/services/rating.py maps to HTTP 409 - is always importable.
#     It carried a direct pin here previously; that pin is removed, because a
#     transitive distribution the planned inventory does not name should not
#     acquire a direct declaration inside a feature change.
#
# -----------------------------------------------------------------------------
# LOAD-BEARING CONSTRAINT: pydantic MUST stay on the 1.x line
# -----------------------------------------------------------------------------
# backend/app/core/config.py:L1 is `from pydantic import BaseSettings`, and
# Pydantic v2 removed `BaseSettings` from the top-level package. Every model in
# this codebase is written to v1 semantics as a result. Weakening this pin makes
# app/core/config.py fail to import, and with it every module that imports
# `settings` - which is to say all of them. It is also why FastAPI stays on a
# release line that still supports Pydantic v1 (see the note below).
#
# -----------------------------------------------------------------------------
# RECORDED FINDING 1: Python 3.9 is past end of life
# -----------------------------------------------------------------------------
# `google-api-core` and `google-auth` emit unsupported-runtime warnings when
# imported on Python 3.9. That is a genuine forward-compatibility signal, so it
# is recorded here rather than suppressed. The runtime target is NOT raised
# unilaterally: .github/workflows/backend_ci.yml:L16-L19 pins
# `python-version: '3.9'` and is the only version source in the repository -
# there is no setup.py, pyproject.toml, tox.ini, setup.cfg or .python-version
# anywhere to widen it - so this manifest honours the documented runtime.
#
# -----------------------------------------------------------------------------
# RECORDED FINDING 2: CI resolves this file from the repository ROOT
# -----------------------------------------------------------------------------
# .github/workflows/backend_ci.yml declares no `working-directory`, so its L24
# `pip install -r requirements.txt` resolves to `./requirements.txt` at the
# repository root, not to this file. scripts/setup_environment.sh:L28 has the
# same shape. Both are pre-existing workflow/script defects, and both are
# recorded rather than repaired: the workflow and the script are declared
# no-change, and this file's path is fixed at backend/requirements.txt. Do not
# relocate this file, do not duplicate it at the root, and do not edit the
# workflow to work around it. Install it explicitly instead:
#
#     pip install -r backend/requirements.txt
#
# -----------------------------------------------------------------------------
# RECORDED FINDING 3: two upgrades are needed and are NOT taken here
# -----------------------------------------------------------------------------
# Both require a change this manifest is not permitted to make on its own, so
# each is stated with the work it needs rather than left implicit:
#
#   * PyPDF2 -> pypdf: TAKEN. The escalation this note used to carry was that
#     the pin could not move without the one-line import change at
#     app/services/document_processing.py:L1, which was then out of scope. That
#     consumer change is delivered, so the pin moved with it and `pypdf==6.16.0`
#     is below. What is still NOT taken is the size/time ceiling around the
#     parse: `extract_text` is called on caller-supplied bytes with no bound on
#     document size or parse duration, and pypdf fixes the known infinite loop
#     without making a large hostile document cheap. That ceiling belongs to
#     whoever owns the upload path.
#   * FastAPI 0.103.2 predates the Content-Type ReDoS fix released in 0.109.1.
#     Upgrading is not a pin edit: FastAPI's newer lines move Starlette across
#     several majors, and FastAPI drops Pydantic v1 support entirely above
#     0.124 (0.128.x will not resolve against pydantic 1.10.13 at all - proven,
#     not assumed). A framework upgrade of that size belongs in its own
#     reviewed change alongside the Pydantic v1 -> v2 migration, not inside a
#     feature. python-multipart is already at the fixed release below.
#
# =============================================================================
# RECORDED FINDING 5: the runtime is NOT raised, and the rest of the closure is
# NOT re-resolved
# -----------------------------------------------------------------------------
# A dependency-security review of this manifest asked for more than the four
# upgrades above: raise the runtime to Python 3.11 and re-resolve the whole
# closure on it (fastapi 0.125.0, pydantic 1.10.26, google-cloud-firestore
# 2.28.1, google-cloud-storage 3.13.1, google-cloud-vision 3.15.0,
# google-cloud-documentai 3.15.0, google-api-core 2.34.0, Pillow 12.3.0,
# pytest 9.1.1, httpx 0.28.1, python-multipart 0.0.32), which closes most of
# the residual advisories in one move. That is a real finding and it is not
# dismissed. It is not taken here, for two reasons that are both about
# something other than this file:
#
#   * THE RUNTIME IS DOCUMENTED, NOT INCIDENTAL.
#     .github/workflows/backend_ci.yml pins `python-version: '3.9'` and is the
#     only version source in the repository. Raising it is a deployment-target
#     decision that belongs with the pipeline and the deployment, not with a
#     feature's manifest, and most of the versions above cannot be installed on
#     3.9 at all (`pytest` 9.x and `Pillow` 12.x both declare
#     `requires-python >= 3.10`), so the pins and the runtime have to move
#     together or not at all.
#   * THE FIRESTORE PIN IS LOAD-BEARING.
#     app/db/firestore.py bounds this release's THREE unbounded transaction
#     RPCs and its query-stream resume loop itself, against 2.13.1's internals -
#     `_BoundedTransaction` overrides `_begin`/`_commit`/`_rollback`, and the
#     expiring retry predicate is what terminates `Query.stream`. Moving the
#     client is therefore not a pin edit: it needs that bounding re-proved
#     against the new internals, with the availability tests that cover it.
#
# WHAT A HUMAN MUST DO. Take the runtime decision first (3.11 or 3.12; celery
# 5.3.6 states 3.11 as its supported ceiling). Then re-resolve this manifest on
# it as one reviewed change, re-prove the datastore bounding against the newer
# firestore client, and re-run both rating suites. Until then the residual
# advisories on the pins above stand, recorded rather than closed, and every
# pin here is at the newest release that installs on the documented runtime.
# =============================================================================

# --- Authentication ----------------------------------------------------------

# 3.5.0 rather than the planned 3.3.0, which is affected by CVE-2024-33663

# CVE-2024-33664 (JWE token decompression denial of service). Reverting would
# reintroduce both. The decode call in app/api/auth.py relies on the
# `require_exp`/`require_sub` decode options, which this release supports.
python-jose[cryptography]==3.5.0
# passlib: bcrypt password hashing - app/api/auth.py:L5, app/core/security.py.
passlib[bcrypt]==1.7.4
# bcrypt: THE ONE ADDITION to the planned inventory, and a functional
# requirement. passlib 1.7.4 probes its bcrypt backend at CryptContext
# construction by hashing a deliberately over-long secret
# (passlib/handlers/bcrypt.py:detect_wrap_bug). bcrypt 5.0.0 refuses a secret
# over 72 bytes with `ValueError: password cannot be longer than 72 bytes`, so
# an unpinned install makes `CryptContext(schemes=['bcrypt'])` raise and takes
# every password hash and verification with it - measured, not theorised.
# bcrypt 4.1+ additionally dropped the `__about__` attribute passlib reads for
# its version banner, which is only a logged warning but is avoided too. 4.0.1
# is the newest release that is clean on both counts.
bcrypt==4.0.1

# --- Google Cloud ------------------------------------------------------------
# google-cloud-firestore supplies the two primitives this feature is built on:
# DocumentReference.create() (create-only, raises AlreadyExists - the
# one-rating-per-transaction constraint) and the transactional runner behind the
# atomic rating-plus-aggregate write.
#
# THIS RELEASE DOES NOT BOUND ITS OWN THREE TRANSACTION RPCs, AND THE
# APPLICATION BOUNDS THEM FOR IT. In firestore_v1/transaction.py, Commit goes
# through `_commit_with_retry`, whose body is `while True:` retrying on
# ServiceUnavailable with no attempt ceiling and no deadline, while
# BeginTransaction and Rollback are issued with no retry and no timeout at all.
# firestore_v1/query.py compounds it: `Query.stream` resumes a failed stream in
# a `while True` loop, each resume starting a fresh per-attempt deadline. Every
# handler here is synchronous and runs on a bounded threadpool, so any of those
# loops can hold a worker thread for the duration of a datastore outage.
# app/db/firestore.py closes all four: `datastore_call()` builds a fresh policy
# per operation whose predicate expires on a wall clock (which is what ends the
# stream resume loop, since that loop consults the predicate), and
# `_BoundedTransaction` reissues Begin, Commit and Rollback through the same
# generated client with an explicit retry and timeout. Upgrading the pin is NOT
# a substitute for that wrapper - `_commit_with_retry` has the same unbounded
# shape on later 2.x releases - so if this version is ever moved, re-verify
# those two modules rather than assuming the bound came with the upgrade.
google-cloud-firestore==2.13.1
google-cloud-storage==2.13.0
google-cloud-vision==3.4.5
google-cloud-documentai==2.20.1

# --- Background tasks --------------------------------------------------------

# --- Media and document processing -------------------------------------------
# Pillow: app/services/ai_vision.py opens caller-supplied bytes with
# `Image.open(BytesIO(image_data))`, reached from POST /listings, so this decoder
# is on a request path that accepts untrusted input. 11.3.0 rather than the
# planned 10.1.0, which is affected by CVE-2023-50447 (arbitrary code execution
# via ImageMath.eval, fixed in 10.2.0), CVE-2024-28219 (buffer overflow in
# _imagecms, fixed in 10.3.0) and CVE-2025-48379 (heap buffer overflow writing
# DDS, fixed in 11.3.0). 11.3.0 supports Python 3.9 and the code needs no
# change: only `Image.open` is used.
Pillow==11.3.0
# pypdf: app/services/document_processing.py:L1 (`from pypdf import PdfReader`).
# This replaces `PyPDF2==3.0.1`, which was the FINAL PyPDF2 release, warns on
# import that the project moved to `pypdf`, and is affected by an infinite-loop
# denial of service when parsing a hostile document (CVE-2023-36464 /
# PYSEC-2026-1835). No PyPDF2 release fixes it, so the remedy is the successor
# package. The reader API is unchanged across the rename - `PdfReader`, its
# `pages` sequence and `extract_text` are the same names with the same
# semantics - which is why the consumer needed an import change and not a
# rewrite. 6.16.0 declares `requires-python >= 3.9` and resolves with the rest
# of this manifest on CPython 3.9.
pypdf==6.16.0
